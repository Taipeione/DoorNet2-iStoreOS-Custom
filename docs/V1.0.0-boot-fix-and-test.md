# DoorNet2-V1.0.0：启动修复与实机验收

**范围**：基于标准 OpenWrt `v25.12.5`（固定 commit 不变），原有 V0.1 完整源码编译为 V1.0.0。此包仅包含源码；并未在本地构建固件。

## 已修复的构建层风险

1. 历史 `doornet2-v0.1.yml` 实际是修补旧 Release 的 15 秒 TEST 流程，不能当作源码编译。现将它归档至 `legacy/V0.1/`，新建完整 `doornet2-v1.0.0.yml`，只允许运行 `workflow_dispatch`。
2. U-Boot 确保 `mmc0 = &sdmmc` (TF)，`mmc1 = &sdhci` (eMMC)，并在本镜像
   的 `/chosen/u-boot,spl-boot-order` 中声明 `same-as-spl`、TF、eMMC。
   `998-doornet2-tf-first.patch` 改变的是已运行 U-Boot 的 distro 扫描顺序为
   `mmc0 mmc1 ...`，不是 RK3399 BootROM 的初始介质选择。
3. U-Boot 默认使用 `CONFIG_ENV_IS_NOWHERE=y`，避免读取 eMMC 旧版 `boot_targets=mmc1 mmc0 ...` 覆盖本机启动策略。
4. 在本板镜像 gzip 前将 MBR disk signature 设置为 `0xD0021000`（根分区 `d0021000-02`），与默认 OpenWrt 的 `5452574f-02` 分离，避免双介质相同 PARTUUID 让根文件系统串盘。boot.scr 使用动态 `part uuid ${devtype} ${devnum}:2 uuid`，不写死磁盘号。
5. 两种镜像都进行静态检查：MBR 与根分区，32MiB boot，64MiB root，8MiB U-Boot FIT，FIT 内有效 SHA256，实际嵌入的 `boot_targets=mmc0 mmc1`，引导脚本动态解析 PARTUUID；失败则不给正式 Artifact。

## 验收步骤

1. GitHub Actions Run #4 已完成完整 `make`、启动链校验和 SHA256 校验；产物归档与镜像已独立下载并复核。后续实机验收仍必须使用该 Run #4 归档，不使用本地编译结果。
2. **不要先写 eMMC**。检查现有可恢复启动方式，先备份旧 eMMC 的启动区域与用户配置。确认 TF 卡烧录整盘镜像的工具和操作。
3. 使用烧录软件将 `DoorNet2-V1.0.0-squashfs.img.gz` **解压后当整盘镜像**写入 TF 卡，不要只写分区。再确认 TF 首扇区 MBR 和第 2 分区 PARTUUID 是 `d0021000-02`。
4. TF 插入后开机，串口 1500000bps 记录 `TPL/SPL`，`Trying to boot from MMC...`，U-Boot `boot_targets`、`mmc list`、`part uuid mmc 0:2 uuid`、最终 Linux `cat /proc/cmdline`。串口禁止连接 5V 电平，只能使用适当的 3.3V TTL 接口。
5. Linux 成功时确认 `findmnt -n -o SOURCE /`，`blkid`，网口、LuCI、LAN 192.168.100.1/24、DHCP/WAN 和 iStore 实际运行。
6. **断电关机**并拔 TF，检查是否恢复 eMMC 启动；注意此前老 eMMC U-Boot 是否会覆盖/影响 TF 启动。记录现象与串口证据。
7. PassWall、PassWall2、dnsmasq、SmartDNS、AdGuard、微信直连、重启保留配置及 OTA 逐项实测；不通过不发布正式稳定版。

## 仍不能用静态检查证明的内容

- RK3399 BootROM 对初始 TF/eMMC 介质的选择发生在 TF 镜像中的 U-Boot 运行前；
  设备上已有的 eMMC TPL/SPL/U-Boot 可能因此完全绕过本 TF 镜像。
- 真实 1GB DDR3L 初始化、RGMII/PCIe 网卡、硬件电源管理和 U-Boot 执行路径。
- 无法通过单独修改 TF 镜像保证覆盖旧 eMMC BootROM/U-Boot 行为；本工作流不会
  自动写 eMMC。若要改变普通上电的初始来源，必须先取得串口或只读 LAN 证据，
  再单独评估 MR/Flash 安全路径或 eMMC 引导器变更。
