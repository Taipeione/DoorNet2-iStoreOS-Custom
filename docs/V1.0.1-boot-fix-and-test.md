# DoorNet2-V1.0.1：启动来源诊断增强与实机验收

V1.0.1 继续使用标准 OpenWrt `v25.12.5`、RK3399、1GB DDR3L 和
`rockchip/armv8/embedfire_doornet2`。本版本没有修改 eMMC、U-Boot 或
分区，也没有把 BootROM 的不可控选择宣传为已修复。

## 本版本的真实修复范围

V1.0.0 的 TF raw 镜像已经通过 MBR、SPL/idbloader、FIT、MMC aliases、
动态 root PARTUUID 和 U-Boot distro 顺序检查，但实机仍进入原 eMMC 系统。
在没有串口和有效 LAN SSH 证据时，无法证明失败发生在 BootROM、eMMC 旧
TPL/SPL、旧 U-Boot、TF DDR3L 训练或 TF U-Boot 之后。

V1.0.1 因此实施以下可验证改进：

1. OpenWrt Rockchip boot.scr 在读取 root PARTUUID 后输出当前 `${devtype}`、
   `${devnum}` 和 root PARTUUID，便于串口或 U-Boot 日志确认实际启动介质。
2. 新增只读 `/usr/sbin/doornet2-boot-report`，通过 root source、sysfs 控制器
   地址、Device Tree aliases、MMC 卡属性、分区表和 blkid 识别 TF/eMMC。
3. 新增 `doornet2-boot-source` 启动诊断服务，将上述只读摘要写入 volatile
   OpenWrt logring；它不写 block device、U-Boot 环境或分区。
4. 构建门禁验证编译后 boot.scr 中的诊断标记、FIT DTB aliases、SPL 顺序、
   U-Boot `boot_targets`、MBR signature、分区偏移和 root PARTUUID。
5. 所有 V1.0.1 产物的 BuildInfo 明确写入 `hardware_boot=NOT_TESTED`。

这些改进不能改变 RK3399 BootROM 在 TF 镜像执行前的初始介质选择。如果实机
仍然普通上电进入 eMMC，不能仅凭 V1.0.1 的静态通过判定 TF-first 已实现。

## 云端构建

完整固件只通过 GitHub-hosted Actions 构建：

```text
workflow: DoorNet2-V1.0.1
base: OpenWrt v25.12.5
target: rockchip/armv8/embedfire_doornet2
LAN: 192.168.100.1/24
hardware boot: NOT TESTED
```

必须同时通过：

- 完整 OpenWrt 编译；
- SPL/idbloader 非空检查；
- U-Boot FIT 和 hash 检查；
- U-Boot MMC aliases 与 conditional TF-first 顺序检查；
- boot.scr 动态 PARTUUID 和启动来源诊断标记检查；
- MBR `55aa`、磁盘签名 `0xd0021000`、boot/root 偏移检查；
- ext4 与 squashfs 镜像 gzip、fwtool 元数据和 SHA256 检查。

## TF 卡安装边界

1. 只把解压后的 V1.0.1 raw 镜像写入独立 TF 卡整盘。
2. 写入前和回读后分别校验 SHA256。
3. DoorNet2 原 eMMC、eMMC U-Boot、U-Boot 环境和启动分区保持不变。
4. 不执行 sysupgrade，不使用 `dd` 写入 DoorNet2，不擦除 eMMC。
5. 普通上电仍是实验性观察；如果没有 TF 启动迹象，不重复刷写或修改 eMMC。

如果需要使用野火官方的 MR/Flash 安全启动路径，应先记录按钮行为和恢复
路径；这不是本项目自动执行的设备写入操作。

## 实机验收计划

只有真实设备日志或截图才能把项目状态从 `NOT TESTED` 改为 `HARDWARE TESTED`：

1. 记录上电后 LED 和网口状态，不重启循环测试。
2. 通过路由器 DHCP 表确认是否出现 `192.168.100.1` 或实际租约。
3. 通过 LAN-only SSH 运行 `doornet2-boot-report`。
4. 保存 `/proc/cmdline`、`/proc/mounts`、`blkid`、`/sys/class/mmc_host`、
   Device Tree aliases 和 mmc/rootfs 日志。
5. 只有报告证明 root source 为 TF 后，才继续检查 DHCP、WAN、IPv4/IPv6、
   LuCI、iStore、插件生命周期、DNS、OTA 和重启保持。
6. 没有串口时，BootROM/TPL/SPL 的具体阶段仍必须标记 `NOT TESTED`。

## 状态标签

- `BUILD VERIFIED`：GitHub Actions 完整构建、产物校验和 SHA256 通过。
- `STATIC TESTED`：源码、FIT、boot.scr、分区、PARTUUID 和诊断工具通过静态测试。
- `HARDWARE TESTED`：有真实设备日志或截图支持的项目。
- `NOT TESTED`：没有真实设备证据的项目，包括 BootROM 选择、DDR3L 训练、
  TF-first 普通上电、eMMC fallback、网络、iStore、插件、DNS 和 OTA。
